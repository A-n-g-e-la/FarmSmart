# Stage 2C.2B.2: offline callback foundation

The existing `POST /ussd` blueprint remains the only endpoint. No candidate
identification, PIN verification, enrollment, farmer-data access, advisory
requests or SMS delivery is connected. The PIN crypto implementation and its
non-waiting process-wide scrypt gate are unchanged.

## Feature flag and secrets

`USSD_PERSISTENT_FLOW_ENABLED` defaults to `false` in every environment. Only
explicit `true` enables the persistence foundation. A malformed flag fails
closed. With the flag false, the original public, database-independent menu
behavior, parsing, status codes and browser-cookie independence are preserved.
This flag does **not** enable PIN authentication, even when configured correctly.

With the foundation enabled, missing/invalid configuration produces a fixed
plain-text `END` with HTTP 503 before database access. Flask debug mode is refused
before reading callback bodies. Unexpected route exceptions are contained;
configuration/operational diagnostics and submitted values are never returned.
Disable the Werkzeug debugger at the WSGI/hosting layer too; do not expose the
development launcher. Disable request-body/local-variable capture in APM, proxy
inspection, tunnel dashboards and error reporting. No application can enforce
the retention policy of external instrumentation or the provider.

Required settings:

| Setting | Contract |
| --- | --- |
| `USSD_SERVICE_CODE` | Exact configured numeric `*...#` code. |
| `USSD_METADATA_HMAC_KEY` | Canonical base64 encoding of 32 independent secret bytes. |
| `USSD_RELAY_SECRET` | Canonical base64 encoding of another independent 32-byte secret, supplied externally. |
| `USSD_TRUSTED_RELAY_IPS` | Comma-separated exact socket-peer addresses of our own relays; at most eight. No provider IP assumptions, CIDRs, wildcards, duplicate or unspecified addresses. |
| `SECRET_KEY` | Provision a stable Flask key externally for deployment. The existing web-development fallback is unchanged. |
| `USSD_PIN_PEPPERS`, `USSD_PIN_CURRENT_KEY_VERSION` | Valid Stage 2C.1 keyring/current version; checked without hashing even though PIN verification is disconnected. |
| `AFRICASTALKING_API_KEY` | Optional existing provider API credential, checked against relay-secret reuse when supplied; never used to authenticate inbound callbacks. |

The relay credential must differ from every PIN pepper, metadata key, Flask key
and configured provider API key (including `AT_API_KEY`/`AFRICAS_TALKING_API_KEY`
config aliases if used by the host application). Raw and encoded forms are
compared. The existing PIN validator additionally rejects reused pepper keys.
Metadata and Flask keys must differ. No default secret is supplied, logged,
persisted or generated by this foundation. Rotating the metadata key requires
expiring old sessions under the existing persistence contract.

## Trusted relay contract

The sole implemented origin mechanism authenticates **our relay**, not an
Africa's Talking signature. It requires all of:

1. Native HTTPS on the relay-to-backend hop (`wsgi.url_scheme`), without trusting
   `X-Forwarded-Proto`.
2. An exact native `REMOTE_ADDR` match to a configured relay address. ProxyFix
   rewriting is explicitly refused; `X-Forwarded-For` and `Origin` are ignored.
3. `X-FarmAdvis-USSD-Relay` containing the dedicated secret, compared in constant
   time. Missing/incorrect credentials, transport or peers return fixed HTTP 403.

The relay must first verify the external sender using a separately confirmed
provider-origin arrangement, strip any incoming relay-secret header, inject
its own credential, and forward over TLS. Restrict direct backend network access
to these relays. A relay that blindly forwards public traffic does not establish
provider identity. Provider allowlists, signed callbacks, configurable provider
headers, Basic authentication and fixed source ranges are **not** assumed or
implemented. Obtain current capabilities/ranges for the actual account and
environment before exposing real PIN traffic. Callback secrets belong in server
configuration/headers, never callback query strings or URLs.

The trusted gateway, TLS termination and native peer-preservation arrangement
must be validated in hosting; existing arbitrary forwarded-header configurations
will fail closed. No ProxyFix or global web-security behavior is changed here.

## Shared admission interface

Trusted host startup code must install an audited `SharedCallbackLimiter`
subclass at `app.extensions["ussd_shared_limiter"]`, explicitly declaring
`deployment_wide = True`. No working local or external adapter is shipped.
Without a compatible adapter the enabled foundation remains unavailable.
The marker is a deployment contract, not proof of a correctly implemented backend.
The recording test fake must never be installed in a deployment.

`admit(limits)` must use authoritative shared-backend time and atomically apply
all limits in that call across every worker and replica. It must enforce both
sliding-window quotas and token-bucket bursts, refilling each bucket at
`count / seconds`. On denial consume none of that call's quotas. Return literal
`True`/`False` without waiting; exceptions, non-booleans and backend unavailability
fail closed with 503. Capacity denial returns 429. Every response is fixed plain
text beginning `END`; no attempt count/session/authentication change occurs.

Provisional configuration:

| Setting | Default |
| --- | --- |
| `USSD_PHONE_CALLBACKS_PER_MINUTE` | 20 |
| `USSD_PHONE_CALLBACK_BURST` | 5 |
| `USSD_NEW_SESSIONS_PER_MINUTE` | 3 |
| `USSD_GLOBAL_CALLBACKS_PER_SECOND` | 10 |
| `USSD_GLOBAL_CALLBACK_BURST` | 10 |

Global admission follows relay verification and precedes body parsing. A second
atomic call enforces the phone quota plus the initial-callback quota when text
is empty. The phone key is the existing keyed fingerprint, never the raw phone.
Global budget consumed by a later malformed/denied request is intentionally not
refunded. Every duplicate consumes ingress quota; empty retries also consume the
initial quota, conservatively bounding session starts without doing DB reads
before admission. Duplicate callbacks do not repeat persistence effects.

A Redis adapter is a future option; a trusted proxy adapter must provide equally
strong atomic, per-normalized-phone admission and unforgeable decisions. Do not
implement the interface as a counter in a Flask process or accept admission flags
from callback form fields/HTTP headers. Set bounded adapter network timeouts,
bounded key retention/cardinality and fail-closed outage behavior. The public
edge must also bound unauthenticated traffic and connections: application global
admission only counts traffic from authenticated relays.

## Persistence and replay

After the unchanged four-field, URL-encoded parser and 4,096-byte bound:

- Empty text creates a welcome-state session without a farmer binding and its
  position-zero keyed fingerprint/catalog response in one repository transaction.
- An exact live welcome replay only reads the matching session/result. It never
  inserts, refreshes expiry, rebinds a phone or synthesizes previous history.
- If creation fails, one fresh **read-only** reconciliation may recognize an
  independently committed matching welcome. There is no insert retry or loop.
  Missing/conflicting/expired state fails closed. This is safe reconciliation of
  an insert collision or uncertain commit, not a claim that rollback always
  undoes a lost commit acknowledgement.
- From the actual welcome, `0` stores the exit response then ends the session;
  `1` stores the existing verification-unavailable response then ends it; other
  single selections store invalid-selection then end it. Result insertion,
  input-position advancement and ending are one transaction. Any failure rolls
  back the complete unit. Cumulative inputs such as `1*dddd` are refused.
- An exact, still-unexpired terminal replay may return its prior public terminal
  response through reads only. An ended session cannot accept a **new** operation,
  changed input or an empty callback that would reopen it. Expired replay is
  refused as well.
- Phone fingerprints, service code, expected input position, prefix fingerprint,
  lifetime and empty verification metadata are rechecked. Missing history is not
  fabricated. Bound, PIN-state and verified sessions are refused untouched.

This foundation never locks credentials or accounts after sessions: it supports
only unbound sessions and holds no outer transaction around authentication.
Stage 2C.2B.3 must acquire account/profile/credential locks before session locks
and call the existing two-phase authentication service outside an outer unit.

`USSD_SESSION_SECONDS` defaults to 180, capped at 180; the deadline is absolute.
`USSD_RETENTION_SECONDS` defaults to 86400, must cover the lifetime, and is capped
at seven days. These are provisional values requiring provider retry/session-ID
reuse confirmation. Fresh application UTC is checked after reads and writes;
public welcome/terminal transactions do not promise commit-time expiry. The
existing authenticated-transition database-UTC guard remains unchanged. Keep
application/database clocks synchronized. No cleanup scheduler is added; do not
delete retained sessions before confirming the provider replay horizon.

## Remaining work before Stage 2C.2B.3/deployment

- Approve and validate the real relay's external-origin verification and TLS/
  firewall/native peer topology. No origin claims are established by these fakes.
- Implement/audit an actual shared limiter; test cross-worker races, policy
  boundaries, outages and bounded latency. Budget WSGI workers and scrypt memory.
- Add USSD-scoped connection, query and lock-wait timeouts and request deadlines;
  the current shared DB helper remains unchanged. Never rely on a proxy timeout
  to cancel SQL or roll back an in-flight transaction.
- Separately approve isolated MariaDB schema/constraint/locking/UTC validation.
  Offline tests use the real repository with a stateful mocked connector; they
  do not execute SQL or certify InnoDB semantics.
- Confirm optional callback fields, provider retries, terminal events, retention,
  and the success placeholder before changing the four-field parser or menus.
- Wire candidate identification/PIN verification and protected-state checks only
  in the next approved stage. No web enrollment or password fallback is included.
